RESPOSTA:
Com base na sua ideia, a resposta é: **sim, é totalmente viável e existe um ecossistema crescente de ferramentas e padrões que suportam exatamente esse tipo de arquitetura**. A combinação de Markdown com frontmatter TOON, um sistema de arquivos como base de conhecimento e um motor de busca local sem banco de dados é uma abordagem emergente e muito promissora, alinhada com o que pensadores como Andrej Karpathy têm proposto.

A seguir, detalho como você pode estruturar esse sistema, desde a especificação do formato até a arquitetura de busca, incluindo ferramentas que já implementam partes dessa visão.

### 📄 Especificação do Formato de Arquivo: Markdown + Frontmatter TOON

A pedra fundamental do seu sistema é o **TOON (Token-Oriented Object Notation)**. Ele foi projetado especificamente para reduzir o consumo de tokens em comunicação com LLMs, sendo uma alternativa mais eficiente que JSON e YAML.

*   **Eficiência Comprovada**: O TOON pode reduzir o uso de tokens em **40% a 62%** em comparação ao JSON para dados estruturados, principalmente porque elimina a repetição de nomes de chaves em arrays de objetos, usando um formato tabular com um cabeçalho único.
*   **Estrutura Ideal para Snippets**: Para o seu caso de uso, cada arquivo seria um "mini snippet de conhecimento". O frontmatter TOON conteria os metadados estruturados (decisões, contexto, resultado, ajustes), enquanto o corpo do Markdown conteria o conhecimento não estruturado (prosa, explicações, código).

**Exemplo de um snippet de conhecimento (`.md` com frontmatter TOON):**

```markdown
id: "decisao-arquitetura-001"
tipo: "decisao"
topico: "Arquitetura de Busca"
subtipo: "Escolha de Tecnologia"
data: "2026-09-18"
status: "aprovado"
tags: ["busca", "sem-vector-db", "toon", "rag"]
contexto: "Avaliação de alternativas ao RAG vetorial tradicional para base de conhecimento de LLM."
resultado: "Optamos por uma arquitetura file-based usando TOON + BM25."
ajustes_nao_obvios:
  - "O campo 'relevancia_hop' deve ser calculado com base na proximidade semântica, não apenas na correspondência de palavras-chave."
  - "Links entre snippets são armazenados como 'backlinks' no frontmatter para permitir navegação em grafo."
artefatos_relacionados: ["snippet-codigo-042", "nota-tecnica-015"]
---

## Detalhes da Decisão

A abordagem vetorial tradicional apresentou problemas de relevância em consultas que exigiam raciocínio multi-hop. A busca por similaridade tende a retornar resultados "similares, mas não relevantes".

### Justificativa

A arquitetura file-based com TOON permite que o LLM navegue por um grafo de conhecimento explícito, seguindo links tipados, em vez de depender de similaridade implícita.

### Próximos Passos

- [ ] Implementar um índice BM25 sobre os snippets.
- [ ] Criar um script para gerar backlinks automaticamente.
```

### 🗂️ Arquitetura do Sistema: File-Based, Sem Banco de Dados

A sua intuição de evitar um banco de dados é partilhada por várias ferramentas modernas que adotam uma **arquitetura "file-first"**. A ideia central é que o sistema de arquivos *é* o banco de dados.

*   **Ferramentas de Referência**:
    *   **`@dikolab/kbdb`**: Uma base de conhecimento file-based que oferece busca híbrida (palavra-chave + semântica) usando apenas arquivos em disco, sem necessidade de servidor ou conta na nuvem.
    *   **`monkeyllm`**: Transforma seus documentos em um "grafo de conhecimento Markdown versionado por git", onde o agente navega por nós, em vez de receber um "dump" de resultados de busca.
    *   **`ContextTape`**: Uma alternativa ao RAG que armazena texto e embeddings em arquivos segmentados, sem depender de bancos de dados vetoriais como Pinecone ou ChromaDB.

*   **Vantagens da Abordagem File-Based**:
    *   **Portabilidade e Versionamento**: Todo o conhecimento reside em arquivos de texto, que podem ser versionados com Git, copiados, sincronizados e inspecionados manualmente.
    *   **Simplicidade**: Elimina a complexidade operacional de manter um servidor de banco de dados.
    *   **Transparência**: O conhecimento é legível e "inspecionável", ao contrário de índices binários opacos.

### 🔍 Motor de Busca e Recuperação: Navegação em Grafo vs. Busca por Similaridade

Para um sistema de conhecimento otimizado para LLM, a busca não deve ser apenas por similaridade semântica. O ideal é permitir que o LLM **navegue** pelo conhecimento.

*   **Abordagem de Navegação em Grafo (Recomendada)**: Ferramentas como o `monkeyllm` implementam um paradigma onde o LLM "navega" por um grafo de nós Markdown. Em vez de receber fragmentos de texto, o agente segue links tipados (ex: "resolve", "depende de", "relacionado a") para construir contexto de forma ativa. Isso demonstrou melhorar drasticamente a precisão em consultas que exigem múltiplos saltos de raciocínio, superando baselines de RAG tradicional.
*   **Abordagem Híbrida (BM25 + Semântica)**: Ferramentas como `kbdb` combinam busca por palavra-chave (BM25) com busca semântica para obter o melhor dos dois mundos: precisão em termos exatos e flexibilidade para sinônimos.

**Componentes essenciais do motor de busca:**

1.  **Indexador**: Um script (ou ferramenta) que varre o diretório de snippets, extrai o frontmatter TOON e o corpo do Markdown, e constrói um índice em memória.
2.  **Motor BM25**: Para busca por palavra-chave, que é rápida e eficaz para encontrar termos específicos.
3.  **Extrator de Entidades e Links**: Um processo (pode ser assistido por LLM) que analisa o corpo do texto para identificar e criar links entre snippets relacionados, construindo o grafo de conhecimento.
4.  **Interface de Consulta (MCP)**: Expor o motor de busca como um servidor MCP (Model Context Protocol) permite que agentes de IA (como Claude, Cursor, etc.) o utilizem nativamente como uma ferramenta de memória.

### 🛠️ Ferramentas Existentes que Podem Servir de Base

Você não precisa construir tudo do zero. Várias ferramentas já implementam partes dessa visão:

| Ferramenta | Descrição | Relevância para o seu projeto |
| :--- | :--- | :--- |
| **`monkeyllm`** | Motor de conhecimento que transforma documentos em um grafo Markdown. Usa BM25 e navegação por links, sem embeddings. | **Altíssima**. É a implementação mais próxima da sua ideia de "navegação em grafo de conhecimento". |
| **`kbdb`** | Base de conhecimento file-based com busca híbrida (BM25 + semântica) e servidor MCP. | **Alta**. Ótima referência para um motor de busca híbrido leve e sem servidor. |
| **`hyphae`** | Grafo de conhecimento federado, nativo para agentes, construído em Markdown. Usa BM25 sobre SQLite FTS5. | **Média**. Interessante para o conceito de "memória organizacional" e protocolos de escrita segura por agentes. |
| **`ContextTape`** | Alternativa ao RAG que armazena embeddings em arquivos segmentados, sem banco de dados vetorial. | **Média**. Útil se você quiser adicionar uma camada de busca semântica *sem* a complexidade de um banco vetorial. |
| **`PageIndex`** | Motor de RAG "vectorless" que usa um índice de árvore hierárquico e raciocínio do LLM para recuperação. | **Média**. Uma abordagem diferente de "busca por raciocínio" que vale a pena estudar. |

### 💎 Arquitetura Recomendada para o Seu Sistema

Com base na sua ideia e no que foi pesquisado, uma arquitetura recomendada seria:

1.  **Camada de Armazenamento**: Um diretório de arquivos `.md`. Cada arquivo é um snippet de conhecimento autocontido.
    *   **Frontmatter TOON**: Metadados estruturados (decisões, contexto, tags, links para outros snippets).
    *   **Corpo Markdown**: Conhecimento narrativo, explicações, trechos de código não óbvios.

2.  **Camada de Indexação e Busca**:
    *   **Indexador BM25**: Um script (ou ferramenta como `kbdb`) que mantém um índice invertido para busca rápida por palavra-chave.
    *   **Grafo de Links**: Um processo que extrai entidades e relações do corpo do texto (pode usar um LLM local ou a API de um modelo) e as armazena no frontmatter de cada snippet como backlinks.

3.  **Camada de Interface para o LLM**:
    *   **Servidor MCP**: Expor as seguintes ferramentas:
        *   `search(query)`: Retorna os snippets mais relevantes usando BM25.
        *   `get_snippet(id)`: Retorna o conteúdo completo de um snippet.
        *   `get_related(id)`: Retorna os snippets ligados ao snippet atual (navegação em grafo).
        *   `create_snippet(frontmatter, body)`: Permite que o LLM *escreva* novo conhecimento no sistema.

4.  **Fluxo de Trabalho do LLM**:
    *   O LLM, ao final de uma sessão, é instruído a "externalizar" o conhecimento gerado.
    *   Ele usa a ferramenta `create_snippet` para criar um ou mais arquivos `.md` com o frontmatter TOON preenchido.
    *   Ao iniciar uma nova sessão, ele usa `search` e `get_related` para "reconstruir" o contexto necessário de forma eficiente.

Essa arquitetura combina a eficiência token do TOON com o poder de um grafo de conhecimento navegável, tudo sobre uma base de arquivos simples e portável, alinhando-se perfeitamente com a sua visão de um sistema de anotações otimizado para LLM.

Se quiser aprofundar em algum ponto específico, como a implementação do servidor MCP ou a extração automática de backlinks, é só me avisar.

# Schema canônico v1

## 1. Envelope (frontmatter)

Chaves fixas, ordem canônica, valores curtos. Chave desconhecida = rejeita no write.

| chave | tipo | obrigatório | descrição |
|---|---|---|---|
| `id` | string | sim | prefixo de tipo + base36 (ver §3) |
| `k` | enum | sim | tipo (§2) |
| `t` | string | sim | **a afirmação**, não um rótulo. ≤ 120 chars |
| `ts` | iso8601 | sim | criação (UTC, segundos) |
| `c` | float 0–1 | sim | confiança. default `0.7` |
| `tags` | string[] | não | ≤ 5, lowercase, kebab |
| `src` | string \| url | não | proveniência (id de outra nota ou URL) |
| `h` | hex8 | sim | xxhash64 do corpo (dedup, §7) |
| `v` | int | sim | versão do schema. atual = `1` |
| `exp` | iso8601 | não | expiração (facts temporários) |
| `sup` | id | não | id da nota que esta substitui (§7) |

Sem `title`, sem `author`, sem `created_at`, sem `updated_at` (o evento cobre). Sem campos “para humano”.

**Corpo:** só o que o título não diz. Contexto mínimo, exemplos, código. Sem heading `##`, sem preâmbulo, sem conclusão. Se o corpo repete o título, o corpo está errado.

---

## 2. Tipos (`k`) — enum fechado

```
fact        assertiva verificável
decision    escolha + justificativa
question    aberto, não resolvido
task        ação pendente
def         termo → significado
error       problema + causa + fix
snippet     trecho de código reutilizável
link        referência externa + por quê
meta        conhecimento sobre o próprio sistema
```

Fechado de propósito. Tipo aberto = LLM inventa categoria = retrieval degrada. Se precisar de um novo, é bump de schema, não improviso.

---

## 3. IDs

`<prefixo>_<base36(8)>` — prefixo de 1 letra por tipo:

```
f_ fact      d_ decision   q_ question   t_ task
e_ def       x_ error      s_ snippet    l_ link
m_ meta
```

O prefixo é **filtro de graça**: o LLM lê `f_7a3c` e já sabe o tipo sem parsear frontmatter. Isso economiza tokens em todo `recall`.

Geração: `xxhash64(k + t + ts + random)[:8]` → base36. Colisão: re-rola o random. Colisão real em 10⁹ notas ≈ 0.

---

## 4. Arestas — vocabulário + extração automática

Tipos de aresta (fechado):

```
ref     menção simples
dep     depende de
contra  contradiz
sup     suporta / confirma
ext     estende / refina
repl    substitui (gera sup na outra ponta)
```

O LLM **não declara arestas**. Elas emergem do corpo. Regras:

```python
# menção direta por id
r'\b([fdxqteslm]_[0-9a-z]{8})\b'           → ref

# wikilink
r'\[\[([^\]]+)\]\]'                         → ref

# padrões verbais (só se o alvo for id ou [[id]])
r'\b(depende de|requer|precisa de)\s+(\S+)' → dep
r'\b(contradiz|refuta|invalida)\s+(\S+)'    → contra
r'\b(confirma|reforça|suporta)\s+(\S+)'     → sup
r'\b(estende|refina|generaliza)\s+(\S+)'    → ext
r'\b(substitui|substituído por)\s+(\S+)'    → repl
```

Conservador por design: falso positivo no grafo polui `expand` para sempre. Se ambíguo, não cria.

Extração roda no **write**, não no rebuild — o custo é do escritor, não do leitor.

---

## 5. Tools — assinatura e formato de retorno

Sete tools. Formato de retorno é **parte do schema** (é o que o LLM vê).

### `recall(q, k=10, k_filter=None, tags=None, since=None) -> string`

Retorno em pipe, uma linha por hit, **sem JSON**:

```
f_7a3c|Rust > JSON por decodificador formal|0.91
f_1e09|TOON reduz tokens vs JSON em objetos|0.78
d_4b22|markdown como base|0.65
```

~15 tokens/hit. Sem ids de score redundantes, sem chaves. O LLM decide quais puxar.

### `get(ids: [str]) -> string`

```
f_7a3c
Rust transmite mais informação determinística por caractere que JSON porque
o decodificador (compilador) é formal e compartilhado.
---
f_1e09
TOON reduz 40–62% dos tokens vs JSON em arrays de objetos por eliminar
repetição de chaves via cabeçalho tabular.
```

Separador `---`. Sem frontmatter no retorno (o LLM já viu o título no recall). Meta só se pedido: `get(ids, meta=True)`.

### `expand(id, kind=None, depth=1) -> string`

Mesmo formato de `recall`, mas a terceira coluna é o tipo da aresta:

```
f_1e09|TOON reduz tokens vs JSON|ext
d_4b22|markdown como base|sup
```

### `write(k, t, body, tags?, src?, c?) -> {id, action}`

`action ∈ {created, merged, rejected}`. Ver §6.

### `update(id, patch, reason) -> {ok, prev_h}`

`patch` só aceita `t`, `body`, `tags`, `c`, `exp`. Mudança de `k` = nova nota + `repl`.

### `link(from, kind, to, reason) -> {ok}`

Aresta manual. Raro — só quando a automática falha.

### `forget(id, reason) -> {ok}`

Soft delete. Nota vira `k=meta, status=forgotten`, sai do índice ativo, permanece recuperável por `get` explícito.

**Sem `search`, sem `list`, sem `delete`, sem `stats`.** Sete tools é o teto. Qualquer adição precisa remover outra.

---

## 6. Protocolo de escrita (duas fases)

O LLM não escreve direto. `write` é precedido por `recall` obrigatório:

```
1. LLM monta (k, t, body)
2. write(..., dry=True) → sistema roda recall(t + body[0:200])
   retorna: {candidates: [{id, title, score}], action_hint}
3. LLM decide:
   - score < 0.75  → write() commita, action=created
   - 0.75 ≤ s < 0.92 → write(merge_into=id) → action=merged
   - s ≥ 0.92      → write() rejeitado, action=rejected
4. Commit: fsync + rename, append em events.jsonl, marca dirty
```

O limiar é ajustável, mas **não pelo LLM em runtime** — é config do sistema. Se o LLM controla o limiar, ele aprende a burlar.

---

## 7. Dedup + supersede

- **Dedup:** `h` (hash do corpo normalizado — lowercase, whitespace colapsado) detecta duplicata exata em O(1). Similaridade semântica pega o resto.
- **Supersede:** `update` não sobrescreve. Cria nova versão, marca a antiga com `sup=<novo_id>`, e a antiga vira `status=superseded` — fora do `recall` default, dentro do `expand` com `kind=repl`.
- **Cadeia de supersede** é walkable: `get(id, history=True)` retorna a linhagem.

Isso resolve o problema real que a maioria ignora: **conhecimento muda**. Um sistema append-only sem supersede acumula contradições silenciosas.

---

## 8. Versionamento

`v` no frontmatter + `meta.json` no `.idx/`. Regra: se `v` da nota > `v` do índice, rebuild forçado daquela nota. Se `v` do índice > `v` da nota, migração on-read (nota antiga é lida com defaults).

Sem migração em massa. Sem downtime. O índice é derivado — jogar fora e reconstruir é sempre uma opção válida.

## O que este schema decide (e o que deixa para depois)

**Decide:** tipos, chaves, IDs, arestas, formato de retorno, protocolo de escrita, dedup, supersede.

**Deixa para os próximos dois documentos:**
