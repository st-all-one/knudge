Vamso recapitular então, qual é o panorama geral desse sistema? O que existe nele, como funciona, de que modo pode ser otimizado para simplicidade, visando ser algo fixo no projeto e apeans o utilitário que faz a consulta/escrita ser externalizado?

# Panorama do sistema

## A inversão que define tudo

A maioria dos sistemas de conhecimento otimiza **armazenamento** e depois tenta encaixar o LLM. Este faz o contrário: otimiza o **contexto injetado** e trata armazenamento/índice como detalhe derivado.

Três consequências que explicam todas as decisões:

1. **O usuário é o LLM.** Não há humano lendo, editando ou navegando. Legibilidade humana é irrelevante; tokenização é tudo.
2. **O custo é contexto, não disco.** Índice binário local não vale nada se a resposta injetada for verbosa. A economia está em nunca injetar 10 notas quando 3 bastam.
3. **O índice é derivado.** `notas/` reconstrói `.idx/` do zero. Se isso deixar de ser verdade, o design quebrou.

---

## O que existe no sistema

Quatro camadas, das mais estáveis às mais descartáveis:

### 1. Fonte da verdade — `notas/`

Arquivos `.md` com frontmatter TOON. Uma nota = uma unidade de recuperação. Uma afirmação, fato, decisão ou tarefa por arquivo.

```markdown
---
id: f_7a3c
k: fact
t: Rust > JSON por decodificador formal
ts: 2026-09-18T14:22:00Z
c: 0.9
tags: [rust, tokenizer]
h: a3f7b2c1
v: 1
---
Rust transmite mais informação determinística por caractere que JSON porque
o decodificador (compilador) é formal e compartilhado.
```

Nada aqui é otimizado para humano. Título é a afirmação. Corpo é contexto mínimo. Sem heading, sem preâmbulo, sem conclusão.

### 2. Log de eventos — `eventos/events.jsonl`

Append-only. Toda escrita gera linha. Nunca sobrescreve. Estado atual = fold. É o que permite auditoria, replay e rebuild determinístico. Opcional mas recomendado.

### 3. Índice derivado — `.idx/`

Binário, mmap-friendly, reconstruível. Contém:

| arquivo | conteúdo |
|---|---|
| `terms.idx` / `terms.bin` | índice invertido (termo → posting list) |
| `docs.idx` / `docs.bin` | forward (id → metadados, offsets) |
| `tags.idx` / `tags.bin` | tag → bitmap de doc_ids |
| `graph.idx` / `graph.bin` | adjacência (nó → [kind, target]) |
| `fields.idx` | índice por campo (status, prioridade) |
| `time.idx` / `time.bin` | ordenação temporal |
| `embeddings.jsonl` | vetores (opcional, se quiser proximidade semântica) |
| `clusters.jsonl` | agrupamentos batch (opcional) |

**Regra de ouro:** `notas/` + `eventos/` sempre reconstroem `.idx/` do zero. O índice nunca é fonte da verdade.

### 4. Cache — `cache/`

Respostas caras, embeddings pré-computados, warm start. Descartável a qualquer momento.

## O contrato — o que fica fixo no projeto

Estas são as peças que **não mudam** sem bump de versão. São o que o LLM vê e o que define a semântica do sistema.

### Schema canônico

- **Tipos fechados:** `fact`, `decision`, `question`, `task`, `def`, `error`, `snippet`, `link`, `meta`. Nada fora do enum.
- **Chaves mínimas:** `id`, `k`, `t`, `ts`, `c`, `h`, `v`. Opcionais: `tags`, `src`, `exp`, `sup`.
- **IDs:** prefixo de tipo + base36(8). O prefixo é filtro de graça — o LLM sabe o tipo sem parsear.
- **Arestas:** vocabulário fechado (`ref`, `dep`, `contra`, `sup`, `ext`, `repl`). Extraídas automaticamente do corpo, não declaradas.

### Sete tools — o teto

```
recall(q, k, filters)  → IDs + títulos + score (formato pipe, ~15 tokens/hit)
get(ids)               → corpo completo (só dos IDs pedidos)
expand(id, kind, depth)→ vizinhos no grafo
write(k, t, body, ...) → cria com dedup
update(id, patch)      → versiona, não sobrescreve
link(from, kind, to)   → aresta manual (raro)
forget(id, reason)     → soft delete
```

Sem `search`, `list`, `delete`, `stats`. Qualquer adição precisa remover outra.

### Protocolo de escrita

O LLM não escreve direto. `write` é precedido por `recall` obrigatório:

- score < 0.75 → cria
- 0.75 ≤ score < 0.92 → merge
- score ≥ 0.92 → rejeita

Limiar é config do sistema, não do LLM. Se o LLM controla o limiar, ele aprende a burlar.

### Formato de retorno

Pipe-delimitado, sem JSON, sem chaves redundantes:

```
f_7a3c|Rust > JSON por decodificador formal|0.91
f_1e09|TOON reduz tokens vs JSON em objetos|0.78
```

O LLM decide quais puxar. Corpo só chega via `get`, e só dos IDs pedidos.

---

## O utilitário — o que é externalizado

Um binário (ou servidor MCP) que implementa as sete tools. É a **única** peça que o LLM toca. Tudo mais é invisível.

### O que ele faz

1. **Indexação** — varre `notas/`, valida frontmatter, extrai arestas, constrói `.idx/`. Full rebuild ou incremental (compara mtime + hash).
2. **Query** — parse → valida → planeja → executa (bitmaps + BM25 + opcional cosseno) → funde → ranqueia → limita.
3. **Escrita** — valida schema, roda dedup, commita atomicamente (`fsync` + `rename`), append em `events.jsonl`, marca dirty.
4. **Expansão** — BFS no grafo com profundidade configurável.
5. **Manutenção** — rebuild, compactação de eventos, watcher (opcional).

### O que ele **não** faz

- Não armazena estado próprio além do índice derivado
- Não exige servidor rodando (pode ser CLI ou MCP sob demanda)
- Não tem banco de dados
- Não depende de serviço externo (exceto modelo de embedding, se usado — e mesmo esse pode ser local)

## Como simplificar

O sistema já é enxuto, mas há pontos onde dá para cortar mais.

### Corte 1 — Embeddings são opcionais

Comece **sem** embeddings. TF-IDF + cosseno sobre o índice invertido que você já tem resolve 70% do problema para snippets curtos e técnicos. Se depois precisar de semântica de verdade, adicione `embeddings.jsonl` como derivado — não como fonte da verdade.

**Custo de adicionar depois:** ~20 linhas de numpy. **Custo de começar com:** dependência de modelo, latência no write, complexidade de rebuild.

### Corte 2 — Clustering é batch, não core

Clusters (`clusters.jsonl`) são úteis para o LLM **navegar** sem query específica. Mas rodam no rebuild, não no caminho crítico. Podem ser adicionados como script separado, não como parte do utilitário principal.

### Corte 3 — Watcher é conveniência

`inotify`/`fsevents` é legal, mas não essencial. Rebuild incremental sob demanda (ou a cada N writes) é suficiente. O watcher economiza segundos, não muda o design.

### Corte 4 — Eventos são recomendados, não obrigatórios

`events.jsonl` dá auditoria, replay e rebuild determinístico. Mas se você confia no `h` (hash) do frontmatter para detectar mudanças, pode viver sem. O evento vira o mecanismo de **fold** — se você não precisa de histórico, não precisa de evento.

### Corte 5 — O índice binário pode começar em JSON

A spec do `.idx/` binário (varint, delta, Roaring) é ótima para escala. Mas se você tem <10k notas, um índice em JSON carregado em memória é mais simples de debugar e igualmente rápido. Migre para binário quando o volume justificar — o design permite porque o índice é derivado.

### O mínimo viável

```
notas/           # .md com frontmatter TOON
.idx/
  index.json     # índice invertido + forward + grafo, tudo em JSON
tools.py         # recall, get, expand, write, update, link, forget
```

Sem eventos, sem binário, sem embeddings, sem clusters, sem watcher. Isso roda em ~300 linhas de Python. O resto é otimização incremental.

| Peça | Estabilidade |
|---|---|
| Schema (tipos, chaves, IDs, arestas) | **Fixo.** Bump de versão para mudar. |
| Sete tools (assinaturas e formato de retorno) | **Fixo.** É o contrato com o LLM. |
| Protocolo de escrita (dedup, limiares) | **Fixo.** Limiar é config, não runtime. |
| Estrutura de diretórios | **Fixo.** `notas/` é verdade, resto é derivado. |
| Formato do índice | **Oscila.** JSON → binário quando justificar. |
| Embeddings | **Oscila.** Opcional, derivado. |
| Clusters | **Oscila.** Batch, opcional. |
| Watcher | **Oscila.** Conveniência. |
| Eventos | **Oscila.** Recomendado, não obrigatório. |

O que fica fixo é o **contrato semântico** — o que o LLM vê e como interage. O que oscila é a **implementação do índice** — como o utilitário entrega o contrato de forma rápida.

O utilitário é a única peça externalizada — e pode começar em 300 linhas de Python, evoluindo para binário só quando o volume exigir.

# O que extrair do seeds

O seeds é **arqueologia de decisão**. O sistema que estamos desenhando é **conhecimento atômico**. Eles são complementares — e a parte mais valiosa do seeds é justamente o que o nosso schema ainda não tem.

Vou separar em três blocos: o que vale ouro, o que vale prata, e o que é ruído de domínio (task tracker) que não deve entrar.

---

## Ouro — o que muda o schema

### 1. `alternatives` + `rejected_because`

Este é o padrão mais valioso do seeds inteiro. Ele captura **por que não**, que é exatamente o conhecimento que se perde primeiro.

```
"alternatives":[
  {"name":"Usar <picture> em backgrounds","rejected_because":"CSS background-image não suporta <picture> nativamente."},
  {"name":"Criar serviço de imagem unificado","rejected_because":"O Picture component já existe e funciona."}
]
```

No nosso schema, uma `decision` hoje registra a escolha. Não registra as alternativas descartadas. Isso significa que daqui a 3 meses o LLM vai reler a decisão e **propor exatamente a alternativa que já foi rejeitada** — porque não há registro de que foi considerada.

**Como absorver sem inflar o schema:** uma nova aresta `rej` (rejeitada) entre uma `decision` e uma `def` ou `fact` que descreve a alternativa. A justificativa da rejeição fica no corpo da `def`/`fact` alvo.

```
d_4b22 (decision)  --rej-->  e_8f12 (def: "usar <picture> em backgrounds")
                              corpo: "Rejeitada em d_4b22 porque CSS background-image
                              não suporta <picture> nativamente. Requer JS polyfill
                              ou image-set() sem suporte universal."
```

A alternativa rejeitada é um **fato sobre o mundo** (por que aquilo não funciona), não um detalhe da decisão. Por isso merece nota própria, recuperável isoladamente. Quando outro projeto tiver o mesmo problema, `recall("picture em background")` acha a `def` — e ela aponta de volta para a decisão original.

Isso é a diferença entre um sistema que **lembra decisões** e um sistema que **lembra o espaço de decisões**.

### 2. Split container / atômico

O seeds tem dois namespaces: `pl-*` (plan, container) e `sucesu-*` (seed, atômico). O `pl-20db` agrupa 6 seeds via `children` + `adoptedChildren`. O plano tem context, approach, risks, acceptance próprios; cada filho tem os seus.

O nosso sistema hoje é **só atômico**. Isso é correto para recuperação, mas o LLM perde a capacidade de dizer "me dá o panorama deste tema" sem fazer 15 `recall` diferentes.

**Como absorver:** um tipo novo `k=container` (ou reusar `meta` com uma flag). Um container tem título curto, corpo que é uma **lista de ids**, e arestas `ref` para os membros. Não tem corpo narrativo — só agrega.

```
c_9a3c | Otimização WebP no portal | (container)
corpo:
  d_4b22 decisão: markdown como base
  f_1e09 TOON reduz tokens
  e_8f12 picture em background (rejeitada)
  x_7c11 bug: stacking context em modais
```

`expand(c_9a3c, depth=1)` devolve o mapa. `recall("otimização webp")` acha o container, e o LLM decide se desce ou não.

**Regra:** container nunca é fonte de verdade. É uma view explícita. Se um membro é removido, o container é reescrito. Se o container é deletado, nada se perde.

### 3. `risks` como notas de primeira classe

O seeds tem `risks` embutido no plano. Isso é ouro porque risco é **conhecimento preditivo** — "o que pode dar errado". Hoje não temos isso.

**Como absorver:** um tipo `k=risk` com aresta `ref` para a decisão/nota que ele ameaça. Campo `c` é a probabilidade; o corpo descreve o impacto e a mitigação.

```
r_2e09 | Galerias antigas podem não ter WebP gerado | c:0.4
Ameaça: d_4b22 (picture component).
Mitigação: verificar PopulateMissingImages command do Gallery antes do deploy.
```

Risco é **factual e temporal**: pode se materializar ou não. Por isso `exp` (expiração) é útil — um risco que não se materializou em 6 meses provavelmente não vai se materializar.

---

## Prata — vale absorver com cuidado

### 4. `outcome` post-hoc

O seeds tem `outcome: success` no plano fechado. Isso é **verificação empírica** da decisão. Nós temos `c` (confiança *a priori*), mas não temos resultado *a posteriori*.

**Como absorver sem virar task tracker:** uma aresta `res` (resultado) de uma `decision` para uma `fact` que descreve o que aconteceu. Ou, mais simples, um campo `out` no frontmatter de `decision`: `success | partial | failed | abandoned`.

Isso permite ao LLM perguntar "quais decisões falharam?" e aprender com isso. Sem isso, o sistema acumula decisões otimistas que nunca foram verificadas.

### 5. `revision` como contador simples

O seeds tem `revision: 6`. Nós temos cadeia de supersede. A cadeia é mais rica mas mais cara. Um contador simples no frontmatter (`rev: 6`) resolve 80% dos casos: "quantas vezes isso mudou?". Útil para o LLM calibrar confiança — uma nota com `rev: 12` é volátil, uma com `rev: 1` é estável.

Não substitui supersede, complementa. Supersede é para mudanças semânticas; `rev` é para edições incrementais.

### 6. `templates` / moléculas

O seeds tem `sd tpl` com templates nomeados (`feature`, `task`, `bug`). Cada template define quais `sections` são obrigatórias.

Nós temos `k` (tipo) mas não temos seções obrigatórias por tipo. Uma `decision` deveria ter `contexto`, `alternativas`, `resultado`. Uma `fact` deveria ter só o corpo. Uma `risk` deveria ter `mitigação`.

**Como absorver:** um arquivo `templates.yaml` no projeto que mapeia `k` → seções obrigatórias do corpo. O `write` valida. Isso força consistência sem inflar o frontmatter.

```
decision: [contexto, alternativas, resultado]
risk:     [mitigacao]
error:    [causa, fix]
```

### 7. `prime` como tool de entrada

O seeds tem `sd prime` — "output AI agent context". Isso é **uma tool a mais** que o nosso conjunto de sete não tem: um bootstrap que devolve o mapa geral do conhecimento (containers, contadores, últimas decisões) em poucos tokens.

**Como absorver:** adicionar `prime()` às tools. Retorna:

```
containers: 12
notes: 847 (fact 512, decision 89, risk 43, ...)
recent: d_4b22, x_7c11, r_2e09
```

~30 tokens. O LLM sabe onde está antes de fazer qualquer `recall`. Isso muda a qualidade das queries seguintes.

### 8. Git-native como comando explícito

O seeds tem `sd sync` que faz stage + commit do `.seeds/`. É bobo, mas é a diferença entre "o conhecimento está versionado" e "o conhecimento está versionado *e alguém lembra de commitar*".

**Como absorver:** o utilitário tem `sync` que commita `notas/` + `eventos/` com mensagem gerada a partir do evento. `notas/` é fonte da verdade; `eventos/` é o log. Git é o backup, não o índice.

## Ruído — o que NÃO transferir

| Padrão do seeds | Por que não transferir |
|---|---|
| `assignee` | Não há humano. O "assignee" é o próprio LLM. |
| `priority` P0–P4 | Prioridade é da sessão, não da nota. Vira `c` (confiança) ou ordenação por `ts`. |
| `status: open/closed/done` | Ciclo de vida de task. Nosso `forget` + `exp` cobrem o essencial. |
| `blocks` em steps | Já temos `dep`. A diferença é que o seeds embute a aresta no objeto; nós externalizamos. Externalizar é melhor para grafo. |
| `acceptance` (10 critérios) | Específico de task. Mapeia para `question` falsificável, não para tipo próprio. |

| `existing_seed` em steps | Referência a outro issue. Nós temos `ref` e `sup`. |

O seeds é **task tracker com vocação de knowledge base**. O que estamos desenhando é **knowledge base com vocação de memória de LLM**. A tentação é importar o vocabulário de task; a disciplina é importar só a estrutura de conhecimento.

## A observação que fecha o raciocínio

O seeds revela uma dimensão que o nosso sistema não tinha nomeado: **o espaço de decisão**.

Um sistema de conhecimento puro registra *o que é verdade*. Um sistema de decisão registra *o que foi tentado e por que falhou*. O primeiro responde "o que sabemos?". O segundo responde "o que já tentamos?".

Para uma memória de LLM, o segundo é mais valioso — porque o LLM vai propor alternativas, e sem registro do espaço de decisão ele propõe as mesmas alternativas rejeitadas indefinidamente. O `alternatives` + `rejected_because` do seeds é a peça que transforma o sistema de **arquivo de fatos** em **memória de engenharia**.

Absorver isso é o que faz a proposta deixar de ser um RAG bonito e virar algo que **acumula sabedoria** — não só acumula texto.

# O que `sd prime` faz

Vou decompor a função antes de mapear para o nosso sistema, porque a forma dele é mais importante que o conteúdo.

## As seis peças

1. **Marcador de recuperação** — "Run `sd prime` after compaction, clear, or new session". Ele existe porque contexto morre. Não é documentação; é o que sobrevive quando tudo mais some.
2. **Protocolo de fechamento obrigatório** — checklist com "CRITICAL", "NEVER skip this", "Work is not done until pushed". Cinco passos numerados, sem ambiguidade.
3. **Proibições duras** — "Do NOT use TodoWrite, TaskCreate, or markdown files for task tracking". Ele não só diz o que fazer; diz o que *não* fazer, porque o LLM vai derivar para padrões conhecidos se não for impedido.
4. **Referência de comandos inline** — não aponta para `--help`; traz os comandos essenciais na tela.
5. **Receitas de workflow** — "Starting work", "Completing work", "Creating dependent work". Sequências prontas, não primitivas.
6. **Stance default** — "Use seeds for ALL task tracking". Uma regra que fecha a porta para alternativas.

## Por que funciona

Quatro propriedades que se sustentam mutuamente:

- **Auto-contido.** Uma tela. Sem links, sem descoberta, sem "veja também".
- **Prescritivo.** Diz o que fazer, não o que existe. A diferença entre manual e protocolo.
- **Imperativo.** "MUST", "NEVER", "Prohibited". LLM sem hard constraints drift.
- **Feito para perda de contexto.** Não assume que o leitor lembra de nada. O leitor ideal é um LLM que acabou de acordar sem memória.

E o detalhe arquitetural mais elegante: **o sistema serve o próprio manual**. `sd prime` não é um arquivo que o agente precisa lembrar de ler — é uma tool que o próprio sistema emite quando perguntado. O sistema se ensina a quem pergunta.

## O que isso significa para o nosso `prime()`

No turno anterior eu sugeri `prime()` como "bootstrap de contexto, ~30 tokens". Estava errado na escala e no escopo. O `sd prime` mostra que `prime()` é **o contrato operacional inteiro**, não um sumário.

A diferença de conteúdo: o seeds é um *workflow de tasks*; o nosso é um *protocolo de conhecimento*. A forma é a mesma. O conteúdo muda.

### O que o nosso `prime()` deve conter

**Seção estática (protocolo):**

```
# Knowledge Protocol

## Tipos (k)
fact, decision, question, task, def, error, snippet, link, meta, container, risk

## Tools
recall(q, k, filters) → ids+títulos+score (pipe, ~15 tok/hit)
get(ids)              → corpo completo, só dos ids pedidos
expand(id, kind, depth)→ vizinhos no grafo
write(k, t, body, ...)→ cria com dedup obrigatório
update(id, patch)     → versiona, não sobrescreve
link(from, kind, to)  → aresta manual (raro)
forget(id, reason)    → soft delete
prime()               → este documento

## Protocolo de leitura
NUNCA faça dump. Fluxo: recall → seleciona 3-5 → get → expand se preciso.
Corpo só chega via get, e só dos ids que você pediu.

## Protocolo de escrita (obrigatório)
1. Antes de write, chame recall(t + body[0:200])
2. score < 0.75  → cria
3. 0.75–0.92     → merge no id existente
4. score ≥ 0.92  → rejeitado, use update
5. NUNCA escreva sem recall prévio

## Proibido
- Não escreva >1 afirmação por nota
- Não use prosa decorativa ("## Introdução", "Neste documento")
- Não declare arestas manualmente — elas emergem do corpo
- Não repita o título no corpo

## Fechamento de sessão
[ ] 1. Externalize decisões não-óbvias: write()
[ ] 2. Registre alternativas rejeitadas: def + aresta rej
[ ] 3. Registre riscos: risk com c e mitigação
[ ] 4. Marque containers afetados: update()
[ ] 5. sync (stage + commit notas/ + eventos/)
```

**Seção dinâmica (estado):**

```
containers: 12
notes: 847 (fact 512, decision 89, risk 43, question 31, ...)
recent: d_4b22, x_7c11, r_2e09
dirty: 3 notas não-indexadas
last sync: 2026-09-18T14:22:00Z
```

A estática é o contrato. A dinâmica é onde você está. Juntas, ~400 tokens. Isso é o que sobrevive a compaction, clear, ou nova sessão.

## A observação que fecha

O `sd prime` revela algo que a proposta anterior não tinha nomeado: **o sistema precisa de um ponto de entrada que se auto-serve**.

Um knowledge base sem `prime()` é um conjunto de tools que o LLM só usa se souber que existem. Com `prime()`, o sistema se apresenta — tipos, tools, protocolo, estado — numa chamada. É a diferença entre "há um tesouro aqui" e "aqui está o mapa, a chave, e onde você está no mapa".

E a parte mais importante: **o protocolo de fechamento**. O `sd prime` diz "before saying done, you MUST run this checklist". Isso resolve um problema que ainda não tínhamos enfrentado: o LLM termina uma sessão e **esquece de externalizar o conhecimento gerado**. Sem um checklist obrigatório no `prime()`, o conhecimento morre na conversa — que é exatamente o que você quer evitar desde o início.

O `prime()` não é um sumário. É o **ritual de entrada e saída** do sistema.
