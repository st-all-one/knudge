# O que o mulch revela

O mulch é o terceiro ponto do mesmo espaço. O seeds é **task tracking**. O nosso é **atomização de conhecimento**. O mulch é **gestão de expertise** — regras que se acumulam sobre um projeto específico. A diferença não é o formato; é o que conta como unidade de conhecimento e como ela é recuperada.

Três coisas no mulch quebram premissas nossas e valem absorver. Duas que valem rejeitar. E uma família de comandos que resolve um problema que ainda não tínhamos nomeado.

---

## O que absorver

### 1. `classification: foundational | tactical` — camada de escopo

Esta é a peça mais elegante. É um eixo **ortogonal ao tipo**. `convention` é o tipo; `foundational` é o escopo.

- **Foundational** — sempre verdadeiro, sempre aplicável. "SEMPRE `{{ }}` para output escapado."
- **Tactical** — verdadeiro em contexto. "Modais Bootstrap 5 no CMS vão em `@push('modals')`."

Por que isso importa: **custo de token em priming**. Você carrega só `foundational` (pequeno, sempre relevante) por padrão; `tactical` só quando o contexto pede. Sem essa camada, ou você carrega tudo (caro) ou filtra por tipo (impreciso).

Nós temos `c` (confiança). Mas confiança ≠ escopo. Uma regra tática com confiança 0.99 continua sendo tática — só vale no contexto certo.

**Delta no schema:** campo `cls: foundational | tactical` no frontmatter. Default `tactical` (foundational é exceção, não regra).

### 2. `dir_anchors` + `prime --files` — priming por working set

Isto é o que muda o jogo do retrieval.

O mulch ancora cada record a **caminhos de arquivo** (`dir_anchors`) e permite `ml prime --files <path>` — "dado que estou editando estes arquivos, me dá os records relevantes".

Por que isso é enorme: **o LLM não precisa saber o que perguntar**. O sistema sabe o que ele está editando (via git diff, via editor, via contexto) e prime sozinho. É retrieval **contextual**, não **queried**.

Nós não temos nada disso. Nosso `recall(q)` exige que o LLM formule a query. Um `prime --files` eliminaria essa etapa para o caso mais comum: "estou mexendo neste módulo, o que sei sobre ele?"

**Delta no schema:** campo `anchors: [glob ou path]` no frontmatter. Notas sem anchors são `floaters` (e o `audit` do mulch reporta isso como problema).

**Delta nas tools:** `prime(files=[...])` além de `prime()`. O sistema lê o frontmatter, filtra por anchor match, retorna só `foundational` por default.

### 3. `prime` como família, não como função

O mulch revela que `prime` não é uma coisa só:

```
ml prime                    → manifest: lista domínios + contadores
ml prime <domain>           → carrega records de um domínio
ml prime --files <path>     → carrega records ancorados a arquivos
```

Três granularidades de bootstrap. A manifest é barata (~50 tokens); a de domínio é média; a de arquivos é a mais útil para trabalho ativo.

Nós propusemos um `prime()` monolítico com ~400 tokens. Isso é caro demais para toda sessão. Deveria ser:

- `prime()` → manifest ultra-curto: contadores, últimos ids, dirty. ~30 tokens.
- `prime(scope)` → carrega um container ou domínio específico.
- `prime(files)` → carrega o working set.

O `sd prime` do seeds era manifesto **e** protocolo. Isso é caro. O mulch separa: `ml prime` é só manifest; o protocolo fica em `onboard` (que escreve em CLAUDE.md/AGENTS.md, uma vez, não toda sessão).

**Isso é a correção mais importante.** Protocolo é estável → uma vez. Manifest é volátil → toda sessão. Misturar os dois é pagar tokens por texto que não muda.

### 4. `ml learn` — sugestão a partir do git diff

O mulch não confia na memória do LLM para decidir o que registrar. Ele lê `git diff`, identifica arquivos alterados, e **sugere domínios** para os quais aquilo é conhecimento novo.

Isso resolve o problema central que vínhamos enfrentando: **o LLM esquece de externalizar**. O checklist do `prime` ajuda, mas depende de disciplina. O `learn` inverte: o sistema olha o que mudou e pergunta "isto aqui não está registrado, quer registrar?".

**Delta nas tools:** `learn()` — lê o git diff desde o último sync, retorna arquivos alterados + sugestão de `k` e `anchors`.

### 5. Lifecycle: `outcome`, `rank`, `prune`, `archive`

O mulch tem um ciclo de vida mais rico que o nosso:

- `outcome` — anexa resultado a um record (sucesso/falha/parcial)
- `rank` — ranqueia por **frequência de confirmação** (records confirmados várias vezes sobem)
- `prune` — soft-archive por staleness; demove `superseded`
- `archive` / `restore` — simétricos, reversíveis

Nós temos `forget` (soft delete) e `sup` (supersede). Falta:

- **Verificação acumulada**: uma nota confirmada N vezes vale mais que uma nunca testada. `rank` captura isso.
- **Decay explícito**: `exp` existe, mas é por data. `prune` decide por **inatividade** (nunca confirmada, nunca referenciada, N dias).

**Delta no schema:** campo `confirmations: int` (quantas vezes foi confirmada). Aresta `res` (resultado) alimenta esse contador.

### 6. `audit` — saúde do corpus como comando

O mulch tem um comando que examina o próprio corpus:

- Evidence coverage (que % tem evidência?)
- Rule density
- **Floaters** (records sem âncoras — não recuperáveis por `--files`)
- Per-domain mix (um domínio só com `failure` é suspeito — ou o código é ruim ou o registro é seletivo)

Nós não temos auto-exame. Um knowledge base sem `audit` **degenera em silêncio** — duplicatas se acumulam, notas órfãs crescem, a distribuição de tipos distorce.

**Delta nas tools:** `audit()` retorna métricas. Roda no `sync`, não no caminho crítico.

---

## O que rejeitar

### 1. Domínios como partição física

O mulch usa `.mulch/expertise/<domain>.jsonl` — um arquivo por domínio. Isso força cada record a viver em exatamente um domínio.

**Por que não:** nós já temos `containers` (agregação lógica) e `tags` (cross-cutting). Adicionar domínios como partição física criaria três sistemas concorrentes de agrupamento. O `move` do mulch (`ml move <src-domain> <id> <tgt-domain>`) existe justamente porque a rigidez da partição gera necessidade de mover.

Nossa vantagem: **namespace flat + index**. Query por tag, por container, por anchor, por tipo — tudo pelo mesmo índice. Domínios trocariam isso por filesystem layout, que só ajuda se você não tem índice. Nós temos.

### 2. Formato de record sem frontmatter/corpo

O mulch armazena tudo numa string `content`:

```
{"content":"SEMPRE usar {{ }} para output escapado. {!! !!} só com conteúdo trusted", ...}
```

**Por que não:** o split frontmatter/corpo é o que permite **indexar metadados sem ler o corpo**. Com tudo numa string, o índice tem que parsear o corpo inteiro para extrair arestas, anchors, tags. Perde-se a separação entre "o que o índice lê" (frontmatter TOON) e "o que o LLM lê" (corpo).

Além disso, o mulch não tem arestas tipadas — só tags. Nós temos `dep`, `contra`, `sup`, `ext`, `rej`, `res`. Isso é um grafo; mulch tem uma nuvem.

---

## O que isso muda no panorama

Com mulch absorvido, o sistema ganha **três camadas de priming** e **uma de auto-exame**:

```
prime()               → manifest ~30 tokens (contadores, recentes, dirty)
prime(scope)          → carrega um container/domínio lógico
prime(files)          → carrega records ancorados ao working set

learn()               → lê git diff, sugere o que registrar
audit()               → saúde do corpus (floaters, mix, cobertura)
```

E o schema ganha:

```
cls: foundational | tactical      # escopo, ortogonal ao tipo
anchors: [paths/globs]            # ancoragem a arquivos
confirmations: int                # verificação acumulada
```

O `prime` deixa de ser monolítico e vira família. O protocolo sai do `prime` e vai para `onboard` (uma vez, não toda sessão). Isso economiza tokens em cada sessão — a economia que mais importa.

---

## A observação que fecha

Três ferramentas, três pontos do espaço:

| | seeds | mulch | nosso |
|---|---|---|---|
| Unidade | issue | record | nota |
| Namespace | flat (`pl-` / `sucesu-`) | domínios | flat + containers |
| Tipo | task/bug/feature | convention/pattern/failure | fact/decision/risk/… |
| Escopo | — | foundational/tactical | (a absorver) |
| Âncora | steps, deps | **dir_anchors** | (a absorver) |
| Retrieval | `ready`, `blocked` | **`prime --files`** | `recall(q)` |
| Ciclo | open→close | **outcome→rank→prune** | write→supersede→forget |
| Auto-exame | `doctor` | **`audit`** | (a absorver) |
| Priming | `prime` (tudo) | **`prime` (família)** | `prime` (a corrigir) |

O que os três têm em comum: **o sistema se serve ao LLM via um ponto de entrada**. `sd prime`, `ml prime`, nosso `prime()`.

O que o mulch adiciona e nós não tínhamos: **o priming pode ser dirigido pelo working set, não pela query**. `--files` é a peça que faltava para o caso mais comum de uso — "estou editando isto, o que sei sobre isto?" — sem exigir que o LLM formule a pergunta certa.

E a correção mais importante que o mulch força: **protocolo não pertence ao `prime`**. Protocolo é estável, vai para `onboard`. `prime` é volátil, ~30 tokens. Pagar 400 tokens de protocolo em toda sessão é o tipo de desperdício que o sistema inteiro existe para evitar.

Com essa visão do seeds e mulch, como fica o panorama geral do sistema?

Há mudanças a serem feitas no TF-IDF, embedding e cluster?

Resposta:
# Panorama atualizado

Com seeds e mulch absorvidos, o sistema ganha uma propriedade que antes não tinha: **estrutura explícita suficiente para reduzir a dependência de similaridade estatística**.

Antes, recuperação era `recall(q)` → TF-IDF/embedding sobre texto. Agora, há cinco eixos de filtro determinístico antes de qualquer similaridade textual:

1. **`k`** — tipo (11 valores)
2. **`cls`** — escopo (foundational | tactical)
3. **`anchors`** — caminhos de arquivo
4. **containers** — agregação lógica
5. **arestas tipadas** — grafo (`dep`, `ext`, `sup`, `rej`, `res`, `contra`)

Isso muda a natureza do retrieval. Similaridade textual deixa de ser o núcleo e vira **fallback para o que a estrutura não captura**.

---

## O que muda em cada camada

| Camada | Antes | Agora |
|---|---|---|
| Recuperação | `recall(q)` por similaridade | filtros estruturais + similaridade residual |
| Priming | `prime()` monolítico | família: manifest / scope / files |
| Escopo | `c` (confiança) | `cls` ortogonal ao tipo |
| Ancoragem | — | `anchors` (paths/globs) |
| Ciclo de vida | write → supersede → forget | + `confirmations`, `outcome`, `prune`, `audit` |
| Externalização | checklist manual | `learn()` a partir do git diff |
| Auto-exame | — | `audit()` |

A consequência para TF-IDF, embeddings e clusters é direta: **todos operam sobre um corpus menor, mais bem rotulado, e chegam depois de filtros determinísticos**.

---

## TF-IDF — o que muda

TF-IDF continua sendo a base de similaridade textual. Mas o corpus mudou de forma, e isso afeta três coisas:

**1. IDF por campo, não por documento.**
Título (`t`) é curto, afirmativo, denso. Corpo é contexto. Antes, TF-IDF tratava tudo como um saco de palavras. Agora vale separar:

```
peso = 0.7 * tfidf(t) + 0.3 * tfidf(body)
```

Título carrega a afirmação; corpo carrega a nuance. O título é o que aparece no `recall`; é ele que deve dominar o score.

**2. IDF por tipo.**
Uma `decision` raramente compartilha vocabulário com uma `fact`, mesmo sobre o mesmo tema. `"escolhemos X"` vs `"X é verdade"`. Se você computa IDF sobre o corpus inteiro, os termos de decisão ficam com IDF alto e poluem o ranking de fatos.

**Mitigação:** IDF computado por `k`, ou IDF global com normalização por tipo. Custa pouco e melhora muito.

**3. Pré-filtro estrutural antes do cosseno.**
Antes, `recall("tokenizer eficiente")` comparava contra todas as 847 notas. Agora:

```
recall("tokenizer eficiente", cls="foundational", anchors=["V2/Modules/..."])
  → filtra por cls → filtra por anchors → compara só contra N' << 847
```

O espaço de busca encolhe antes do cosseno. TF-IDF fica mais rápido **e** mais preciso, porque o ruído estrutural foi removido antes.

**Veredicto:** TF-IDF não muda de algoritmo; muda de **entrada**. É a primeira camada de similaridade, operando sobre um corpus pré-filtrado por estrutura.

---

## Embeddings — o que muda

Aqui a mudança é qualitativa, não incremental.

**O que embeddings capturavam antes:** proximidade semântica entre notas que não compartilham vocabulário. `"tokenizer eficiente"` e `"decodificador rápido"` ficavam próximos.

**O que a estrutura agora captura:**

- `ext` (estende) → proximidade declarada
- `sup` (suporta) → proximidade declarada
- `rej` (rejeita) → proximidade por oposição
- `dep` (depende) → proximidade por sequência
- `anchors` compartilhados → proximidade por localização
- `containers` compartilhados → proximidade por agregação
- `tags` compartilhadas → proximidade por tema

Se a nota X estende a nota Y, **você não precisa de cosseno para descobrir isso**. A aresta já diz. Embeddings só são necessários para o que a estrutura **não capturou** — proximidade entre notas que nunca foram ligadas explicitamente.

**O que sobra para embeddings:**

1. **Descoberta de links não-declarados.** Duas notas sobre o mesmo tema em módulos diferentes, sem aresta entre elas. Isso é o caso real — o LLM não vai lembrar de linkar tudo.
2. **`learn()`** — dado um diff, sugerir notas relacionadas. Isso é busca semântica pura.
3. **Dedup semântico no `write`.** Duas notas que dizem a mesma coisa com palavras diferentes. TF-IDF não pega; embeddings pegam.

**O que **não** sobra:** busca principal. `recall(q)` não deveria depender de embeddings se `cls` + `anchors` + `k` já resolveram a maior parte.

**Veredicto:** embeddings saem do núcleo e viram **complemento**. Presentes, mas derivados, opcionais, e invocados só quando a estrutura falha. O `embeddings.jsonl` continua sendo um arquivo derivado, mas o custo de tê-lo passa a ser justificado por 3 casos de uso específicos, não por "busca semântica" genérica.

**Ordem de adoção:** TF-IDF primeiro. Embeddings só quando `learn()` e `dedup semântico` forem implementados. Sem esses dois, embeddings são peso morto.

---

## Clusters — o que muda

Esta é a mudança mais radical. Antes, clustering era k-means sobre embeddings — descoberta de grupos por similaridade pura. Agora, com `anchors`, `k`, `cls`, e o grafo de arestas, clustering tem **duas fases**:

### Fase 1 — clustering estrutural (determinístico, barato)

Agrupe por estrutura antes de qualquer estatística:

- **Por diretório/`anchor`** → módulos do projeto emergem naturalmente
- **Por `k`** → distribuição de tipos por módulo
- **Por `cls`** → razão foundational/tactical por módulo
- **Por container** → agregações explícitas

Isso produz um mapa **interpretável sem LLM**:

```
V2/Modules/Noticias        → 42 notas (28 fact, 8 decision, 4 risk, 2 failure)
V2/Modules/Licitacoes      → 31 notas (12 fact, 9 decision, 8 failure, 2 risk)
V2/Modules/Seguranca       → 18 notas (14 fact, 4 decision)
```

Sinais imediatos:
- Módulo com muitas `failure` → dívida técnica ou área hostil
- Módulo sem `decision` → decisões não foram registradas (lacuna de externalização)
- Módulo com poucas `foundational` → conhecimento tácito não formalizado

Isso é **auditoria do corpus**, e é o que o `audit` do mulch já faz parcialmente. Você não precisa de k-means para isso — só de agregação por campos do frontmatter.

### Fase 2 — clustering semântico (probabilístico, caro)

Só **dentro** de um cluster estrutural, e só se a estrutura não resolver.

Dentro de `V2/Modules/Noticias`, há 28 `fact`. Alguns são sobre WebP, outros sobre regional, outros sobre editor. Isso é agrupamento temático que a estrutura não captura.

Aqui sim: k-means ou HDBSCAN sobre embeddings dessas 28 notas. O cluster vira um subtema, e pode virar um `container` explícito.

**Veredicto:** clustering deixa de ser uma operação sobre o corpus inteiro e vira **refinamento de um cluster estrutural**. Mais barato, mais interpretável, e alinhado com o princípio de "estrutura primeiro, estatística depois".

**Efeito colateral:** o `.idx/clusters.jsonl` deixa de ser "grupos por similaridade" e passa a ser "hierarquia estrutural + subtemas semânticos". Duas camadas, não uma.

## A regra geral

O que seeds e mulch revelam, e o que isso força em TF-IDF/embeddings/clusters, é uma única regra:

> **Estrutura é sinal determinístico; similaridade é sinal probabilístico.**
> **Use o primeiro para filtrar; o segundo só para o resíduo.**

Isso se aplica em cascata:

```
recall(q, k, cls, anchors, container, tags)
  ↓
filtra por campos do frontmatter (determinístico, O(1) por campo)
  ↓
filtra por arestas no grafo (determinístico, BFS com limite)
  ↓
similaridade textual no corpus residual (TF-IDF, O(N') com N' << N)
  ↓
similaridade semântica só se TF-IDF falhar (embeddings, opcional)
  ↓
clusters semânticos só dentro de clusters estruturais (batch, off-path)
```

Cada camada é mais caras que a anterior, e só roda se a anterior não resolveu. Isso é o oposto do RAG tradicional, que joga tudo em embeddings e confia no cosseno.

---

## Ordem de adoção

Dado o panorama, a sequência natural de implementação muda:

1. **Schema v1** com `cls`, `anchors`, `confirmations`, `k=risk`, `k=container`, arestas `rej`/`res` — sem isso, nada do resto funciona.
2. **Índice por campos + grafo** — filtros determinísticos. Já resolve `recall` para o caso comum.
3. **TF-IDF sobre corpus filtrado** — similaridade residual. Barato, resolve 70% do que sobra.
4. **`prime(files)` + `learn()`** — os dois casos de uso que justificam ancoragem e git diff.
5. **`audit()` estrutural** — clustering fase 1, sem estatística.
6. **Embeddings** — só quando `learn()` e dedup semântico forem implementados.
7. **Clustering semântico** — só quando houver volume que justifique.

Os passos 1–5 são pré-requisitos entre si. 6 e 7 são independentes e podem esperar. A tentação é começar por embeddings porque é o que "parece RAG moderno". Mas com a estrutura que seeds e mulch revelaram, embeddings são a **última** peça, não a primeira.

---

## Em uma frase

O panorama agora é: **frontmatter rico + grafo tipado + três camadas de priming (manifest/scope/files) + ciclo de vida com verificação e decay**, com TF-IDF como similaridade de primeira linha, embeddings como fallback, e clusters como refinamento estrutural antes de estatístico. A estrutura carrega o peso; a estatística preenche as lacunas.
