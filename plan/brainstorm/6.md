Valeria a pena envolver ou extender esse sistema para um MCP proativo? No sentido de: ELe acompanha e monitora o que está sendo tratado no chat (principal e subagentes) e, diante de certas flags ou gatilhos, ele injeta conhecimento durante a execução do agente?

REPOSTA:
# MCP proativo — vale, mas estreitamente

Sim, vale. Mas não pela razão que parece.

A tentação é pensar "o MCP fica esperto e injeta conhecimento útil". O problema: **isso contradiz o princípio central do sistema** — nunca injetar mais do que o necessário. Um MCP que injeta por gatilho pode virar um gerador de ruído que consome exatamente o recurso que o sistema existe para preservar: atenção do agente.

A pergunta certa não é "vale?". É "**em que pontos a injeção proativa é estritamente melhor que a query explícita?**".

E a resposta é: quando o **comportamento do agente já é uma query implícita** que ele não formularia.

---

## Os três gatilhos que valem

### 1. Pré-`write` — o caso mais forte

O protocolo já exige `recall(t + body)` antes de `write`. Isso é manual. O agente pode pular, esquecer, ou fazer mal.

**Proativo:** o `write()` retorna, na própria resposta, os quase-duplicados:

```
write(k=fact, t="Blade {{ }} escapa", body="...")
→ {ok: true, id: "f_9a3c", hints: [
    "f_7c11 (0.89) similar",
    "d_4b22 (0.72) contradiz"
  ]}
```

Zero custo de query. O agente já ia escrever; ganha a informação de graça. Se os hints são ignorados, nada se perde. Se são úteis, evitam duplicata.

**Por que é o mais forte:** o momento do `write` é o único em que a duplicata é *acionável*. Depois de commitada, o custo é reconciliação offline. Antes, é decisão.

### 2. Pré-edição de arquivo — `prime(files)` contínuo

O agente edita `picture.blade.php`. Isso é sinal. O MCP sabe que existem notas com `anchors` apontando para esse arquivo.

**Proativo:** ao editar um arquivo, o MCP anexa ao retorno da tool os **títulos** de notas ancoradas (não os corpos):

```
edit("V2/.../picture.blade.php", ...)
→ {ok: true, hints: [
    "d_4b22 picture component como padrão",
    "x_7c11 bug: stacking context em modais"
  ]}
```

~30 tokens. O agente decide se puxa. Se o arquivo já foi tocado na sessão, suprime (dedup por sessão).

**Por que vale:** este é o caso "estou mexendo nisto, o que sei sobre isto?" — mas contínuo, não só no boot.

### 3. Fechamento de sessão — o contador que faltava

Antes do `forget`/`sync`, o MCP verifica:

- Quantos arquivos foram editados nesta sessão?
- Quantas notas foram escritas?
- O diff é significativo mas o write é zero?

Se sim, injeta **uma** linha: `"diff: 12 arquivos alterados, 0 notas escritas. learn()?"`.

Não é um checklist. É um sinal. O agente decide se ignora.

**Por que vale:** resolve o problema "o LLM esquece de externalizar" sem depender de disciplina. O sistema lembra.

---

## O que **não** vale

- **Injeção por similaridade de texto na conversa.** Agente menciona "tokenizer" de passagem, MCP injeta 10 notas. Ruído.
- **Injeção por padrão de erro.** Agente erra, MCP busca falhas similares. Falha muito (o erro é ambíguo, o corpus é raro). Deixar para o agente pedir.
- **Injeção por "decisão detectada".** LLM não tem sinal confiável de "estou decidindo". Falso positivo domina.
- **Injeção contínua ambiente.** Um bloco persistente que atualiza. Contexto infla sem o agente notar.

Regra: **gatilho só quando o comportamento do agente é inequívoco**. Editar arquivo é inequívoco. Dizer "tokenizer" não é.

---

## O mecanismo — três restrições

1. **Todo hint é sugestão de query, não conhecimento.** Nunca injeta corpo. Injeta `id + título + score`, ou `id + título`. O agente decide puxar via `get()`.
2. **Hints são deduplicados por sessão.** O que foi injetado uma vez não volta. Se o agente ignorou, é sinal de que não era útil.
3. **Cap duro por tool call.** Máximo 3 hints. Se há mais candidatos, ordena por score e corta.

Isso é o oposto do RAG. RAG injeta *conteúdo*. Aqui injeta *ponteiros*. O conteúdo só chega quando o agente pede — o que preserva o princípio de "o LLM decide o que puxar".

---

## Como o sistema "ganha o direito" de injetar

Se o MCP começa injetando tudo, vira ruído. Se começa injetando nada, ninguém usa.

**Proposta:** modo observação por N sessões. O MCP registra *que hints teria injetado*, mas não injeta. Ao final de N sessões, o `audit()` mostra:

```
hints propostos: 847
hints seguidos (agente chamou get() no id): 312 (37%)
hints ignorados: 535 (63%)
```

Só os gatilhos com taxa de seguimento > 50% entram em produção. Os outros ficam em observação. Isso é **calibração empírica de proatividade**, não design a priori.

Sem isso, o MCP adivinha. Com isso, ele aprende.

---

## O que isso muda no panorama

Adiciona **uma tool** (`hints()` — opcional, para o agente pedir "o que você tem para mim agora?") e **um comportamento implícito** em `write()` e nas tools de edição.

Não muda schema, não muda índice, não muda protocolo de escrita. É uma camada de **apresentação** sobre o sistema existente. O sistema continua reativo por dentro; ganha uma face proativa por fora.

---

## Em uma frase

Vale, mas o MCP não deve ser **proativo** — deve ser **reativo a comportamento**. O agente já está dizendo o que precisa ao editar arquivos e ao escrever notas; o MCP só precisa ouvir e oferecer, não impor. Três gatilhos, um formato de hint (ponteiro, não conteúdo), cap duro, e um período de observação antes de produção. Fora disso, é ruído pagando com o recurso mais caro do sistema.

## A incorporação

### 1. Um campo `status` unificado

Não é campo só de task. É o eixo que faltava ao lado de `k`, `cls`, `c`.

```
status: active | in_progress | blocked | closed | superseded | forgotten
```

Cada tipo usa o subconjunto que faz sentido:

| `k` | transições válidas |
|---|---|
| `task` | active → in_progress → closed |
| `question` | active → closed (respondida) |
| `decision`, `fact`, `def` | active → superseded |
| qualquer | active → forgotten |

**Default do `recall`:** só `status=active` ou `in_progress`. Tudo mais é filtro explícito.

`forget` deixa de ser tool; vira `update(id, status=forgotten)`.
`sup` deixa de ser aresta; vira `update(id, status=superseded, sup=<novo_id>)`.
`close` deixa de ser tool; vira `update(id, status=closed)`.

Três mecanismos viram um. **Isto é a simplificação real.**

### 2. `priority` e `claimed_by` — só em `k=task`

```yaml
k: task
status: in_progress
priority: 0          # 0-4, default 2
claimed_by: master   # master | subagent-<id>
```

Fora de `task`, esses campos não existem. `write(k=fact, priority=0)` → rejeita.

### 3. `ready` e `blocked` como views, não tools

Computadas no `recall`, não materializadas no índice:

```
recall(k=task, status=open, blocked=false)   → ready
recall(k=task, status=open, blocked=true)    → blocked
```

`blocked` = existe aresta `dep` para nota com `status ≠ closed`, transitivo.

Compute on-read é O(grau × profundidade). Para 847 notas com ~100 tasks, sub-milissegundo. Não vale materializar.

### 4. Acceptance criteria — inline por default, promovível

O seeds tem `acceptance: [10 critérios]` como campo estruturado. Isso força 10 strings por task. Custo alto.

**Nosso default:** critérios no **corpo da task**, como lista markdown. Sem campo, sem nota separada. O LLM lê o corpo e valida.

**Promoção:** se um critério é complexo o suficiente para merecer contexto próprio, vira `k=question` com aresta `ref` da task. Aí ganha ciclo de vida próprio, é buscável isoladamente, e o `close` da task pode exigir que as `question` filhas estejam `closed`.

Sem cerimônia forçada. Promoção só quando justifica.

### 5. Outcome — já proposto, agora com semântica clara

`out: success | partial | failure | abandoned` — só quando `status=closed` ou `status=superseded`.

Aplicável a: `task`, `decision`, `risk`, `question`. Qualquer coisa que possa ser confirmada ou refutada empiricamente.

## Orçamento de tools revisado

O teto de "sete" morreu. O critério agora é: **uma tool por verbo irredutível**.

```
recall(q, filters)          → leitura. Cobre ready/blocked/priority via filtros.
get(ids)                    → corpo
expand(id, kind, depth)     → grafo
write(k, t, body, ...)      → criação
update(id, patch)           → modificação (inclui status)
link(from, kind, to)        → aresta manual
prime(mode, scope)          → bootstrap (manifest | scope | files | audit)
learn()                     → sugestão a partir do diff
sync()                      → commit
forget(id, reason)          → atalho para update(status=forgotten)
```

Dez. `close`, `claim`, `ready`, `blocked`, `hints`, `audit` deixaram de ser tools — viraram filtros, updates, ou comportamentos. Isso é a simplificação que `status` unificado comprou.

**Regra mantida:** adicionar tool exige remover outra. `forget` já está na corda bamba — se sumir, ficam nove.

## O fechamento

O sistema final é:

```
.knowledge/                  # por projeto, independente
  notas/*.md                 # verdade — frontmatter TOON + corpo
  eventos/events.jsonl       # auditoria (não ordem)
  templates.yaml             # seções por tipo
  .idx/                      # derivado, reconstruível
  mulch.config.yaml          # config

um binário: kb
  kb recall / get / expand
  kb write / update / link / forget
  kb prime / learn / sync
  kb serve --mcp             # modo servidor

schema: k + cls + status + c + rev + out
        anchors + tags + src
        arestas: ref dep contra sup ext repl rej res
```

**O que ele é:** knowledge base com ciclo de vida, task tracker com grafo tipado, e priming dirigido por working set.

**O que ele não é:** task tracker com knowledge acoplado (seeds), nem knowledge base com tasks acopladas (mulch). É um sistema onde `k=task` é um tipo entre onze — não um subsistema.

A consequência filosófica: **gerir tarefas deixa de ser um modo separado**. Uma task é uma nota com campos a mais. `recall(k=task, status=open, blocked=false)` é a fila de trabalho. `recall(k=fact, cls=foundational)` é o conhecimento sempre-verdadeiro. Mesma tool, mesma estrutura, mesma sintaxe.

Isso é o que o seeds e o mulch não conseguem: eles *precisaram* de subsistemas separados porque o núcleo deles era um só (issue / record). O nosso núcleo é a **nota atômica** — e tudo cabe nela.

-- PERGUNTA --
realmente preciso de um sistema de prioridade, assignee e acceptance?

# Não. Nenhum dos três.

Cada um desses campos resolve um problema que **você não tem**. Vou mostrar qual problema cada um resolve, e por que ele não aparece aqui.

---

## `priority` — resolve *o que fazer primeiro*

Prioridade existe para **triagem humana**. Há mais tarefas do que capacidade, há múltiplos stakeholders, há deadlines externos. O humano olha a fila e decide.

No seu sistema:

- **Um projeto por vez.** Não há fila competindo.
- **Um par de agentes.** Master orquestra; não há pool disputando work.
- **Sem stakeholder externo.** Ninguém vai cobrar.
- **Sem deadline.** `exp` cobre o raro caso de algo temporal.

O que sobra é "por onde começo?". Isso **não precisa de campo**. O LLM olha `recall(k=task, status=open, blocked=false)`, lê os títulos, e escolhe com base na conversa. Ordenar por prioridade só faz sentido se a ordem importa independente do contexto — e aqui o contexto *é* a ordem.

**Sem `priority`.** Se um dia precisar, ordem por `ts` (mais antigo primeiro) ou por `rev` (mais volátil primeiro) resolve sem campo novo.

---

## `claimed_by` / `assignee` — resolve *quem está fazendo*

Assignee existe para **coordenação entre humanos**. Evita dois humanos pegarem a mesma tarefa. Permite "o que o João está fazendo?".

No seu sistema:

- **Orquestração serial.** O master define o escopo; o subagente executa. Um por vez.
- **Sem ambiguidade.** "Quem está fazendo" é "a sessão atual". Não há outra sessão.
- **Sem necessidade de visão externa.** Ninguém pergunta "o que o agente X está fazendo?" — o agente X é a sessão.

**Sem `claimed_by`.** Se um dia houver duas sessões, o campo nasce aí — não antes.

---

## `acceptance` — resolve *como verificar*

Critérios de aceitação existem para **handoff**. O humano que pediu define o que conta como pronto; o humano que executa sabe quando parou; o humano que revisa sabe o que checar.

No seu sistema:

- **Sem handoff.** O mesmo agente que abre a task fecha.
- **Sem revisor.** Não há segunda parte.
- **Sem definição a priori.** O critério de "pronto" emerge durante a execução, não antes.

O que sobra é: **o corpo da task**. Se o agente precisa lembrar o que era "pronto", escreve no corpo. Isso é uma frase, não um campo estruturado com N itens.

**Sem `acceptance`.** Se um critério é complexo a ponto de merecer ciclo de vida próprio (pode ser respondido, refutado, adiado), vira `k=question` com `ref` da task. Isso é raro o suficiente para não justificar campo.

---

## O que fica no lugar

Não é que tarefa não tem estrutura. É que a estrutura que sobra é **menor**:

| Necessidade real | Como é atendida |
|---|---|
| O que está pronto para fazer? | `recall(k=task, status=open, blocked=false)` |
| O que está bloqueado? | mesma query, `blocked=true` |
| O que já foi feito? | `status=closed` |
| O que fazer primeiro? | ordem por `ts` — sem campo |
| Quem faz? | a sessão atual — sem campo |
| Como verificar? | corpo da task — sem campo |
| O que deu errado? | `out=failure` (campo único) |

**Sobram dois campos**: `status` e `out`. Nada mais.

---

## Onde os três moram, se um dia voltarem

Nada é deletado do espaço de possibilidades. Se um dia:

- **Múltiplos projetos competindo** → `priority` volta
- **Múltiplas sessões simultâneas** → `claimed_by` volta
- **Handoff entre sessões** → `acceptance` volta

Cada um desses é um **sinal de mudança de contexto**, não de tipo de tarefa. Enquanto o contexto for "2 agentes, 1 projeto, orquestrado", os três são cerimônia.

A regra: **campo só nasce quando a ausência dele causa perda real**. Não antes.

---

## O que isso muda no schema

Corta três campos, deixa dois:

```yaml
k: task
status: open | in_progress | blocked | closed | forgotten
out: success | partial | failure | abandoned   # só quando fechada
dep: [ids]                                     # aresta, não campo
```

O resto da task está no corpo. O `status` é o único campo que muda com o tempo. `out` é registro pós-fato. `dep` já existia.

E a tool `update` perde três patches possíveis: `priority`, `claimed_by`, `acceptance`. Ganha nada em troca. Fica mais simples.

## Em uma frase

Prioridade, assignee e acceptance são **resíduos de workflow humano** que sobreviveram na tradução. Nenhum resolve um problema que você tem. O que sobra de estrutura de tarefa — `status`, `out`, `dep`, e o corpo — já está no schema. Cortar os três não perde nada, e limpa o schema de campos que a IA ia preencher por inércia.

O verdadeiro teste: **se você removesse `priority` hoje, o sistema funcionaria exatamente igual?** Se sim, o campo é cerimônia. E é.

## A conexão com `AGENTS.md` — que é o ponto que você fez

Você nomeou o que eu não tinha visto: **validators globais já existem**. Estão no `AGENTS.md`, em prosa.

```markdown
# AGENTS.md
- Sempre rodar phpstan level 9 antes de commitar
- Testes V2 Unit devem passar
- Não usar asset('storage/') diretamente
```

Essas diretivas são validators **implícitos**. O sistema deveria:

1. **Reconhecer** que o `AGENTS.md` é a fonte de verdade para validators globais
2. **Permitir** que o catálogo os nomeie e os torne executáveis
3. **Aplicar** automaticamente a toda task que toca os `anchors` relevantes

Então a resolução de `checks` para uma task vira:

```
checks(task) = checks_explícitos(task)
             ∪ validators_globais(AGENTS.md)
             ∪ validators_por_anchor(anchors(task))
```

Três fontes. A task só declara o delta. O resto é derivado.

**Exemplo prático:** a task de WebP declara `checks: [sniffcss-depth12]`. O sistema adiciona automaticamente `phpstan-9`, `phpunit-v2` (globais) e `no-storage-url` (porque `anchors` inclui `V2/Modules/Noticias/**`, e esse validator tem `scope: ["V2/**"]`).

O agente escreve `checks: [sniffcss-depth12]`. O sistema expande para 5 validators. A cerimônia cai 10×.

---

## O que isso NÃO deve ser

- **Não é prosa.** Critério em texto livre volta a ser interpretação. Comando ou nada.
- **Não é por task.** Se o critério é o mesmo em 30 tasks, define uma vez.
- **Não é declarativo.** O agente não diz "passei no phpstan". O sistema roda o comando e registra a saída.
- **Não é subsistema.** Validators são config. Não têm `k`, não entram no grafo, não aparecem em `recall`. São tabela de referência.

A tentação seria fazer `k=validator` como tipo de nota. **Não.** O comando é config; a *explicação* do porquê um validator existe pode ser `k=meta` com `ref` ao nome do validator. Dois lugares, cada um com a natureza certa.

---

## Onde os resultados moram

Resultado de validator é **evidência**, não conhecimento. Não vira nota.

Opções:

1. **No frontmatter da task, campo `ev`** — `{phpstan-9: pass@2026-09-18T14:22, ...}`. Rápido, morre com a task.
2. **No `events.jsonl`** — cada execução é um evento. Auditável, sobrevive a `forget`.
3. **Ambos** — `ev` para leitura rápida, evento para auditoria.

Recomendo (3). O `ev` é o que o `recall` lê; o evento é o que o `audit()` lê. E se um validator falha consistentemente em módulos diferentes, isso é um `k=risk` ou `k=error` esperando para nascer.

---

## O que isso muda no schema

Adiciona **um campo** e **um arquivo**:

```yaml
# na nota
checks: [validator-names]    # só em k=task
ev: {validator: result@ts}   # preenchido no close
```

E o `out` ganha semântica derivada: se todos os checks passam, `out=success` é inferido. Se algum falha, `out=partial` ou `failed`, dependendo da severidade. O agente não declara — o sistema computa.

## Em uma frase

Você está certo, e a forma certa não é o `acceptance` do seeds — é **referência a um catálogo de validators executáveis**, com `AGENTS.md` como fonte dos globais e `anchors` para aplicação contextual. A task declara o delta; o sistema expande. Fechamento vira evidência, não declaração. E nada disso é subsistema — é uma tabela de config e um campo na task.
