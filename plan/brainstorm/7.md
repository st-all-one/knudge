RESPOSTA:
# Sim. Três relevantes, três secundários.

Fui por comando dos dois tools e marquei o que já foi absorvido. Sobra isto:

## Relevantes

### 1. `diff` — evolução temporal do conhecimento

O mulch tem `ml diff [--ref]` — "mostra mudanças nos records desde um ref git". Não temos nada equivalente.

Por que é grave: o sistema inteiro gira em torno de **conhecimento que muda**. Temos `rev`, `sup`, `out`, cadeia de supersede. Mas nenhum deles responde à pergunta que o agente realmente faz:

> "Meu entendimento de X mudou nos últimos 3 meses? O que mudou?"

Casos concretos:
- Antes de tomar uma decisão nova, quero saber se o entendimento do domínio mudou recentemente.
- Depois de `learn()`, quero ver o que foi escrito nas últimas N sessões para não repetir.
- No `prime`, quero saber "o que é novo desde a última vez que estive aqui".

A cadeia de `sup` dá o *rastro* de uma nota. `diff` dá a **visão agregada** de um período. São coisas diferentes.

**Forma:** `diff(since, until, scope)` → lista de notas criadas, atualizadas, superseded, com `k`, `anchors`, timestamp. Formato pipe, como `recall`. ~5 tokens por linha. Filtra por escopo (container, anchor, k).

### 2. `compact` — consolidação de redundância acumulada

O mulch tem `ml compact [domain]` — analisa candidatos e aplica consolidação. Não temos.

Por que é grave: o sistema acumula. Depois de 100 sessões, há 15 notas sobre "como tratar imagem no portal", cada uma adicionando um detalhe, cada uma escrita em contexto diferente. Nenhuma é duplicata exata; nenhuma é superseded; o `recall` retorna 15 títulos quase-idênticos. O LLM puxa 3, perde os outros 12, e o entendimento fragmenta.

`dedup` no write resolve duplicata **no momento da escrita**. `compact` resolve **acúmulo gradual** — o que ninguém viu acontecer porque cada nota individualmente fazia sentido.

**Forma:** `compact(scope)` → analisa clusters de notas similares, propõe fusões:

```
proposta 1: fundir f_1e09, f_2c44, f_5a12 → f_9b3c
  tema: "TOON reduz tokens"
  perda: nenhuma
  ganho: -2 notas, corpo consolidado
```

O agente aceita, rejeita, ou edita. O `compact` **propõe**, não impõe. É batch, roda no `sync` ou sob demanda.

**Por que é diferente do mulch:** mulch compacta *records do mesmo domínio*. Nós compactamos por similaridade dentro de escopo, sem domínios. Mais flexível, mais complexo. Mas o ganho é grande.

### 3. `plan` — decomposição generativa

O seeds tem `sd plan` — pega uma task grande e spawna children estruturados. `step.blocks` define ordem. Cada step tem tipo, título, prioridade. `plan submit` valida e cria os filhos.

Não temos. E o `container` **não cobre isso**.

`container` é **agregação**: eu tenho 10 notas existentes, agrupo. `plan` é **decomposição**: eu tenho 1 task grande, quebro em 6 sub-tasks, que passam a existir.

São operações inversas. E a segunda é mais comum do que parece: o LLM, ao receber uma task "otimizar WebP no portal", naturalmente a decompõe. Hoje, ele decompõe *na conversa* e as sub-tasks morrem na conversa. Com `plan`, elas viram notas.

**Forma:** `plan(task_id, steps)` → cria as notas dos steps, cria arestas `dep` conforme ordem, marca a task pai com `sub=<ids>`. O `blocked` da task pai depende dos filhos.

Isso é o que transforma o sistema de "registro de conhecimento" em "motor de execução". Sem `plan`, o LLM pensa em árvore mas escreve em lista.

## Secundários

### 4. `restore` — simétrico a `forget`

Temos `forget` (soft delete) mas não `restore`. Assimetria perigosa: se o agente esquece algo por engano, é irrecuperável via tool.

**Forma:** `restore(id)` → `update(id, status=active)`. Uma linha. Mas precisa existir explicitamente, porque o LLM não vai adivinhar que `update(id, status=active)` é a operação de undo.

### 5. `onboard` — instalador do protocolo

O mulch tem `ml onboard` — escreve/atualiza o snippet em `CLAUDE.md`/`AGENTS.md`. Mencionamos isso uma vez, mas não formalizamos.

Sem isso, o sistema não tem **como se instalar em um projeto novo**. O usuário tem que lembrar de escrever o protocolo no `AGENTS.md` manualmente. Isso é exatamente o tipo de cerimônia que mata adoção.

**Forma:** `onboard()` → escreve bloco padrão em `AGENTS.md` com: como invocar o binário, protocolo de fechamento, referência ao `validators.yaml`. Idempotente (substitui bloco anterior).

### 6. `config` — parâmetros externalizados

O mulch tem `ml config` — lê/escreve `.mulch/mulch.config.yaml`. Nós mencionamos o arquivo mas não formalizamos o acesso.

Por que importa: **os limiares do sistema precisam ser ajustáveis sem recompilar**. Limiar de dedup (0.75/0.92), TTL do `forget`, profundidade default do `expand`, cap de hints do MCP, ordem default do `prime`. Tudo isso é config.

**Forma:** `config get/set/list`. Simples. Mas precisa existir.

## O que isso muda no panorama

Duas coisas grandes:

**1. O sistema passa a ter três verbos de transformação**, não um:
- `write` — cria
- `compact` — funde (muitas → uma)
- `plan` — decompõe (uma → muitas)

Sem `compact`, o sistema cresce monotonicamente. Sem `plan`, o LLM pensa em árvore e escreve em lista. Ambos são **irreversíveis de fazer na mão** — o LLM não vai lembrar de consolidar, nem de materializar a decomposição.

**2. O sistema passa a ter memória temporal explícita** via `diff`. Sem ele, o conhecimento é um *snapshot*; com ele, é um *fluxo*. Isso muda o que o `prime` pode responder: não só "onde estou", mas "o que mudou desde a última vez".

E o orçamento de tools cresce:

```
recall, get, expand          → leitura
write, update, link, forget,
  restore                    → escrita
prime, diff, learn           → bootstrap
plan, compact                → transformação
audit, sync                  → manutenção
onboard, config              → instalação
```

~16 tools. O teto de "sete" morreu há dois turnos. O critério agora é: **uma tool por verbo irredutível**. `compact`, `plan`, `diff` são verbos novos. Não são filtros, não são campos, não são variações de `update`.

## A observação que fecha

O que mulch e seeds ensinam, depois de tudo, é que um sistema de memória de LLM tem **três tempos**:

- **Presente:** `recall`, `get`, `expand` — o que sei agora.
- **Passado:** `diff`, `sup`, `rev` — como cheguei aqui.
- **Futuro:** `plan`, `risk`, `question` — o que ainda não sei.

Nós cobrimos bem o presente, razoavelmente o futuro, e quase nada o passado. `diff` é a peça que fecha o triângulo. Sem ele, o sistema é uma fotografia; com ele, é um filme.

E o segundo aprendizado: **consolidação é a única operação que o LLM nunca faz sozinho**. Criar, ele cria. Decompor, ele decompõe na cabeça. Mas fundir 15 notas em 3 exige ver as 15 simultaneamente — o que o recall capado por tokens nunca mostra. `compact` é a operação que o sistema precisa fazer **pelo** LLM, porque o LLM não consegue fazê-la.
