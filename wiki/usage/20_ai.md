# 20 · `kd ai` — a memória/log de um agente

## Para que serve

Consulta, **read-only**, a memória de um **agente** que guarda as notas fora de `notas/` — hoje um
**JSONL** de linhas `{"frontmatter": {…}, "body": "…"}`, o mesmo schema do knudge. É a porta para o
knudge ser o **eixo único de memória**: qualquer agente que exponha esse JSONL passa a ser
consultável pelo `kd`, sem código novo e sem o knudge aprender o formato interno de ninguém.

| Área | O que lê |
|---|---|
| `memory` (default) | a **memória** do agente — `.agents/memory/notes.jsonl` |
| `session-log` | a **projeção** do log de sessão em notas derivadas — `.agents/memory/session-log.jsonl` |

O log de sessão **não** entra como domínio novo: quem o projeta é o **agente** (uma nota derivada
por afirmação, com `provenance.activity=derive`); o knudge só a indexa. O log continua a ser do
agente — uma só verdade.

## Quando usar

- **Use** quando o agente guarda a memória num store próprio (JSONL) e você quer pesquisá-la com o
  motor do knudge (BM25 + âncoras + grafo + RRF).
- **Use `kd ai session-log`** para responder "o que fizemos sobre X?" **entre** sessões, por
  significado, em vez de reler logs.
- **Use `kd ask --agent <nome>`** quando a memória **já** está em `notas/` e só quer filtrar por
  **quem** produziu cada nota.
- **Não use** para escrever na memória do agente: o `kd ai` é read-only. Gravar é do agente.

## Sintaxe

```
kd ai [memory|session-log] [QUERY...] [--source PATH] [--limit N]
```

- A **área** é posicional e tem default `memory`; um valor fora do conjunto falha com exit `2` e a
  lista das opções.
- **Sem** query, **lista** a fonte (`id|tipo|statement`, ordenado por `id`).
- **Com** query, faz **recall** sobre a fonte (`id|statement|score`).
- `--source PATH` aponta uma fonte explícita (por omissão, o caminho convencional da área).

## Exemplos

```bash
# 1. o que há na memória do agente?
kd ai

# 2. buscar na memória do agente
kd ai memory "rate limit do gateway"

# 3. buscar na projeção do log de sessão
kd ai session-log "por que trocamos o modelo de embedding"

# 4. uma fonte fora da convenção
kd ai memory --source /tmp/outra.jsonl "parser TOON"

# 5. enxuto, para um agente ler
kd ai memory "dedup" --limit 3 --json
```

### Filtrar por proveniência (no `ask`)

Quando a memória **já** está em `notas/`, a proveniência (D207) é filtrável:

```bash
kd ask --agent ktu "rate limit do gateway"        # só o que o ktu registou
kd ask --activity derive --type meta "sessao"     # só o que foi projetado de logs
kd ask --agent ktu,goose "dedup"                  # vários (vírgula ou repetição)
kd ask --params '{"query":"dedup","agent":["ktu"]}'
```

## O que esperar

- **Fonte ausente** ⇒ lista vazia e exit `0` (não é erro: o agente pode não ter memória ainda).
- **Linha malformada** ⇒ é ignorada com um **aviso** em `stderr` (a leitura nunca derruba); em
  `--json` o aviso vai em `warnings[]`.
- **`--json`** devolve `{area, source, query, data}` (e `warnings[]`), com `data.hits[]` ou
  `data.notes[]`.
- A ordem é **determinística** (`id` asc), então a mesma fonte dá sempre o mesmo resultado.

## Como um agente expõe a sua memória

1. Emitir notas no **schema do knudge** (uma afirmação por nota; `statement` curto) — o JSONL é
   `{"frontmatter": …, "body": …}` por linha.
2. Preencher `provenance.agent` e `provenance.activity` (`write`/`learn`/`import`/`derive`).
3. Ligar ao código com `anchors` (glob).
4. Se tiver log cru: **projetá-lo** em notas derivadas (`activity=derive`) e apontar o `kd ai` a
   esse ficheiro — nunca ingerir o log como nota canónica.
